Content Refresh Prioritization

Does a Decision Tree beat a simple search-performance rule at flagging pages for content refresh? Both were trained and evaluated on the same client-holdout split — 30,000 pages across 32 anonymized clients — so this paper reports a finished comparison, the feature importance behind it, and what it means for a content team.

Abstract

Can search-performance and content signals a team already has be used to decide which webpages to prioritize for content refresh? This project frames the task as a binary decline classifier (is_declining) backed by a ranked score, using a public-safe, anonymized release of the FlyRank ML Internship dataset — 30,000 page records across 32 clients. A simple search-performance rule was compared against a Decision Tree Classifier (max_depth=4) trained on 15 features spanning search demand, content length, 90-day traffic, and engagement. Both approaches were evaluated on an identical client-holdout split, so no client appears in both training and testing, and a leakage review removed outcome-derived fields — including trend_pct and several derived flag columns — before any model was trained. On this split, the baseline rule slightly outperformed the Decision Tree (87.93% vs. 87.17% accuracy), and the tree's decisions were dominated by a single signal, impressions_90d, at nearly 82% of feature importance, with scroll_rate, clicks_90d, and content_age_days contributing secondary signal. The results are reported as decision-support evidence for a human reviewer, not a validated prediction of search outcomes.

01

Problem statement

Content teams managing large page inventories can't manually re-audit every URL. Some pages are quietly losing visibility, some are ranking well but not converting clicks, and most are simply fine — without a structured way to triage, review time goes wherever someone happens to look, not where it's actually needed.

This project supports the decision of prioritizing webpages that may benefit from a content refresh. The unit of analysis is one webpage belonging to one anonymized client; the output is a binary decline flag (is_declining) plus a ranked list backed by a decision tree score. A content team reviews the ranked/flagged pages and decides what to check first, instead of manually reviewing hundreds of pages one by one — across the 30,000 rows and 32 clients in this dataset, that manual review isn't practical.

03

Methodology

Workflow

Problem framing → data analysis → feature and leakage checks → baseline construction → model training → validation → action recommendations, in that order.

Model choice

A Decision Tree Classifier (max_depth=4, random_state=42) was chosen for interpretability — it exposes which of the 15 signals actually drives a decline flag, rather than acting as a black box.

Baseline

A simple search-performance rule, applied with no fitting, evaluated on the exact same client-holdout split as the Decision Tree — the fairest possible comparison.

Leakage check

Outcome-derived fields — trend_pct, health_score, ai_opportunity, is_underperformer, is_initial_refresh_candidate, is_quick_win, needs_ctr_fix, needs_engagement_fix — were identified and excluded before training. client_id was used only for the holdout grouping, never as a feature.

Key findings

Client-holdout, measured

On the client-holdout split, the baseline slightly outperformed the Decision Tree — 87.93% vs. 87.17% accuracy. The tree's own decisions turned out to be dominated by a single signal.

05

Limitations & honest framing

Every claim above is decision-support evidence, not a validated result. Specifically:

  • Decision-support

    The model does not guarantee improved rankings — it flags candidates for review, nothing more — and on this evaluation it did not outperform a simple baseline rule (87.17% vs. 87.93%).

  • Decision-support

    The model does not predict or model a search engine's ranking algorithm; no causal refresh-impact claim is made anywhere in this project.

  • Directional

    The model relies heavily on one signal (impressions_90d, ~82% of importance), which may make it brittle for pages with mixed or unusual performance patterns.

  • Directional

    The model mainly depends on available search-performance features rather than deeper content-quality signals — many candidate features carried effectively zero importance.

  • Decision-support

    The project was evaluated on the FlyRank ML Internship Starter dataset, not production data — treat every number as a demo-scale signal, not an operating benchmark.

06

Ranked recommendations

In the order a content team should apply them:

  1. Use the model ranking to decide which pages a human reviewer should check first.

  2. Compare the model ranking with the baseline before making content decisions, since the baseline currently performs at least as well.

  3. Review the signals behind each flagged page — especially impressions_90d and scroll_rate — before recommending a refresh.

  4. Check every new feature for data leakage before adding it to the model.

  5. Retrain and re-validate the model when new search-performance data becomes available — a human reviews every flag before action is taken.
